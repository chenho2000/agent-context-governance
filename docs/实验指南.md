# 实验指南：从跑通到理解

所有 Python 片段都在项目根目录以 `uv run python` 运行。每个实验建议使用新的状态目录；重复 append 会产生新事件，这是运行轨迹的一部分。

## 实验一：看清四份文本的差异

先运行 `uv run context-lab demo`，打开打印的报告所在目录。

1. 在 `01-raw.txt` 找到两份旧支付代码。它们内容相同，但 ID 和工具调用 ID 不同。
2. 在 `02-preprocessed.txt` 找到第二份读取对应的 `[unchanged ref:...]`。它不是新代码，只是引用第一次读取。
3. 在 `03-governed.txt` 找到第一份读取的 `[ref:...]`。正文移出活动视图，数据库原文和 sidecar 仍存在。
4. 在 `04-recovered.txt` 核对旧代码，注意它仍然是**修改前**的版本。
5. 在 `trace.json` 查找 `alias_recovery_exact`。这项断言验证“别名 → 源对象 → 归档”的组合没有断链。

思考：如果只按文件路径去重，第三次读取文件已经改变会怎样？如果第一次读取 1—30 行，第二次读取 31—60 行，又会怎样？本实现同时要求路径、版本、范围和内容哈希相同。

## 实验二：亲手操纵一个治理计划

```python
from context_lab.store import Store
from context_lab.governance import Governor
from context_lab.types import Action, Plan

store = Store("runs/manual-gc")
old = store.append("case", "旧实现的详细输出\n" * 100, turn=1, tool="read_file")
store.append("case", "金额必须精确到分", turn=2, kind="user")

g = Governor(store)
snap = store.snapshot("case")
plan = Plan("case", snap.revision, [Action(old.id, "fold")], "manual")
print(g.stage(plan))
print(g.commit("case", expired=True))
print(store.recover("case", old.id))
g.close()
```

尝试把 target 改为当前用户消息：rehearsal 会拒绝。尝试把 action 改为 prune：没有显式 obsolete 标记时也会拒绝。规则系统无法凭空推断哪些对象真的过时，所以离线分支宁可保守。

注意：`rehearse` 可以准备 sidecar，但不改变活动视图。这是“准备恢复材料”和“提交上下文变更”两个不同阶段。失败预演可能留下未被使用的 sidecar，本项目不自动清除它们。

## 实验三：复现异步分支的竞态

```python
future = g.fork("case")  # 请在 close 前运行这一段
store.append("case", "用户新增要求：保留原始响应", turn=3, kind="user")
plan = future.result()
g.stage(plan)  # StalePlan：必须重新生成计划
```

关键不在于线程跑得快还是慢，而是 `fork` 在启动前捕获 revision。后来发生的 append、busy 状态变化、视图提交都会改变 revision。

再实验：`store.set_busy("case", 1)` 后生成并 stage 一个当前版本的计划，提交会因工具在途而失败。设为 0 会再次改变 revision，需要重新规划。原型选择保守的完整重规划；生产系统可以做更精细的计划重基，但必须重新验证依赖。

## 实验四：让缓存决定“先不压”

```python
from context_lab.cache import commit_value

print(commit_value(5000, 4500, future_calls=1))
print(commit_value(5000, 4500, future_calls=200))
print(commit_value(5000, 4500, future_calls=1, expired=True))
```

这里 I=5000、J=4500 是**首个变更位置之后的整段后缀**，不是被删除对象自身的大小。默认写入价 1.25、读取价 0.1。

- 缓存有效、只再使用一次：净收益为 `50 - 5175 = -5125`，缩短仍可能贵。
- 缓存有效、再使用 200 次：净收益 `10000 - 5175 = 4825`。
- 缓存已过期、使用一次：原本两条路径都要写，省下 `500 × 1.25 = 625`。

把编辑点从历史开头移到结尾，即使删除量一样，J 也会改变。`Governor.commit` 会实际计算前后请求的共同教学前缀，不让你手动猜 J。

这里假设未来文本不继续变动、价格线性、整个前缀都可缓存。真实服务还有缓存粒度、模型 tokenizer、供应商规则与命中概率。参数对比用于理解，不用于直接报账。

## 实验五：PRISM 的四个开关

```python
from context_lab.demo import graph_fixture

p = graph_fixture()
for flags in ({}, {"n1": False}, {"n2": False}, {"n3": False}, {"n4": False}):
    r = p.retrieve("为什么 Ada 改变支付方案？", budget=80, **flags)
    print(flags, r["intent"], r["units"], [(e["id"], e["path"], e["cost"]) for e in r["evidence"]])
```

N1 关闭后只取 episode 层向量锚点；N2 关闭后因果边不再享受折扣；N3 关闭后按路径成本顺序选证据；N4 关闭后不再按查询推断因果意图。

本例每条 episode 很短，某些开关可能不改变最终结果。这是应该保留的观察，不能为证明模块有效而篡改数据。把预算从 80 改为 30 或 0，查看证据整体是否还能装入；系统会跳过过大的 episode，可能得到空结果，不会为了凑足 top-K 越过预算。

在 `trace` 里看实际关系边和单步代价；`evidence[].path` 是对应候选的最小成本路径。`candidate_ids` 是进入最后选择阶段的候选，不等于最终发给模型的全部内容。

这个图需要显式构建。如果要接大量真实对话，应增加带来源校验的图抽取器与持久向量索引；当前实现使用全量编码和小图搜索，适合看清机制。

## 实验六：SimpleMem 的“现在”和“从前”

打开 `examples/memory.json`，理解 `content` 与 `metadata.facts` 的关系。前者是原始材料，后者是为离线实验提供的事实标注。

尝试添加第三条事实：

```json
{
  "entity": "Ada",
  "slot": "payment_plan",
  "value": "transactional_outbox",
  "text": "Ada 在 2026-09-07 将方案改为 transactional outbox。",
  "date": "2026-09-07"
}
```

不加 correction：这是随时间改变，两个时点的事实都保留。加 `"correction": true`：把同实体/槽位的其他值标成被此事实更正；默认检索排除被更正项，但 `include_superseded=True` 可查审计历史。

现已支持显式 `supersedes: [memory_id]`，可只更正指定记录。旧 `correction: true` 仍是便于教学的推断模式，只考虑较早观测；复杂有效日期范围不由它自动推理。完整更正关系由事务校验，成环时整个窗口回滚。

再把 `date` 改成 `yesterday`，删除来源对象的 `metadata.date`：应该拒绝，而不是拿机器当前日期猜。可用 `metadata.bindings` 提供明确指代映射，例如 `{"她": "Ada"}`；这是人工授权的消歧标注，不是自动实体链接器。

```python
from context_lab.memory import SimpleMemory
from context_lab.store import Store

m = SimpleMemory(Store(".context-lab"), "memory")
print(m.retrieve("Ada", entity="Ada", date_from="2026-09-05", date_to="2026-09-06"))
```

日期过滤默认针对事实的事件日期，不是“系统什么时候知道这个事实”。完整双时态模型仍是扩展点。

## 实验七：模型主动分页，而非自动塞入全部历史

```python
from context_lab.memgpt import MemoryAgent
from context_lab.providers import ReplayModel
from context_lab.store import Store

s = Store("runs/paging")
for i in range(8):
    s.append("paging", f"payment event {i}", turn=i + 1, kind="user")
a = MemoryAgent(s, "paging", capacity=3000)
model = ReplayModel(
    [
        {"tool": "recall_search", "args": {"query": "payment", "page": 0}, "request_heartbeat": True},
        {"tool": "recall_search", "args": {"query": "payment", "page": 1}, "request_heartbeat": True},
        {"answer": "已查看前两页；这是脚本回放，不是真实模型的理解结果。"},
    ]
)
print(a.run(model, "查找 payment 历史"))
```

`request_heartbeat=true` 请求立即进入下一轮内存操作；false 会交回调用者。默认最多 6 步，避免无限循环。超出工作记忆容量报错，提醒调用者缩小结果或增大预算。

`ReplayModel` 让你清楚看调度；替换为 `Ollama("phi3.5")` 才是实际模型决定工具。Core 可写、Recall 查原始记录、Archival 查派生事实。要在新会话显式使用旧档案，可构造 `MemoryAgent(store, "new-session", archival_session="memory")`；这只共享指定档案，Recall 仍查当前会话。

## 实验八：Sleep-time 的两个时钟

```python
from context_lab.memgpt import SleepWorker

worker = SleepWorker(s)
future = worker.start("paging")
# 主程序在这里可以做独立工作。
print(future.result())
worker.close()
```

没有 facts 标注、也没有模型时，普通文本不会神奇地变成记忆，结果应为空。换用 memory 示例的会话，或者传入模型后再观察。

后台任务基于启动时的快照写派生记忆，不直接修改主会话活动上下文。它记录 `source_revision`，因此后来追加的消息要等下一次整理。这里使用一个工作线程，不具有跨进程任务队列的重试、锁与去重保障。

## 实验九：结构地图不是文件全文缓存

```bash
uv run context-lab codemap src/context_lab --state runs/code-map
uv run context-lab codemap src/context_lab --state runs/code-map --file governance.py --symbol Governor.rehearse
```

返回带装饰器的精确起止行和当前文件哈希。修改该文件后不重建地图，再读符号会收到 stale 错误。删除文件并重建，旧条目就消失。只支持 Python AST；装饰器、嵌套类和方法会进入限定名称。

地图构建仍扫描源文件，只是后续请求不必发送整个文件。地图长度减少不等于端到端模型费用同比下降，工具 schema 与调用往返也有成本。

## 实验十：对比文本压缩与对象治理

```python
from context_lab.compression import cascade
from context_lab.providers import ReplayModel

print(cascade("INFO same\n" * 100, 20))
print(
    cascade(
        "背景材料非常多。" * 100, 60, model=ReplayModel([{"summary": "派生摘要：需要幂等键，金额按分。"}])
    )
)
```

规则只清理确定的冗余。如果文本不够短，可选编码器或本地摘要接棒。仍无法达到预算时抛出 `BudgetError`。没有某档模型时跳过该档，不用假输出替代。

对错误栈、diff、表格等稀疏材料，压缩器保留原文；需要降低活动长度时由 Governor 使用可恢复 fold。当前任务明确需要精确内容时，要标记 `exact_now`，连 fold 也不允许。

模型摘要里的每个断言不一定被原文支持。派生内容带来源标签，是为了可核查；结构校验不能替代语义核查。

## 实验十一：看懂训练候选的边界

demo 中两个候选动作面对完全相同的 prefix 和后续证据需求：fold 保留恢复通路，prune 丢失必需证据。裁判据此生成一个合成偏好对。

打开 `training_candidates/sft.jsonl`：输入只含行动时能看到的信息，不能包含 `required_ids` 等未来需求。打开 `dpo.jsonl`：chosen/rejected 必须针对同一状态和同一评估目标。不同任务的“成功答案”和“失败答案”不能随便配成一个偏好对。

当前 success 仅指明确证据集合仍可用；cost 是可见对象数加恢复对象权重，故意标注为合成评价。真正训练还需要模型生成轨迹、任务级裁判、实际成本、数据去重、隐私处理、训练与独立评测，不能把导出了 JSONL 当成数据飞轮已经改善模型。

## 实验十二：提出一个你自己的反例

最有价值的学习不是只看“省了多少”，而是主动构造以下情况：

- 旧文件快照已折叠，但用户要求比较修改前后的某一行。
- 一份日志只有中间一条错误重要，首尾都看不出问题。
- 一段看似过时的说明仍是当前配置选择的依据。
- 计划生成期间用户追加了禁止条件。
- 检索最相关的两条证据互相矛盾。
- 摘要把“不能重复扣款”变成“可以重试扣款”。

前四类已有结构保护与负例测试。最后两类主要是语义问题，本原型不会宣称已经完全解决：它保留来源和多版本，给进一步核查留下通路。
